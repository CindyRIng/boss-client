## 0. 背景与目标

- 目标：把 BOSS直聘（网页版）封装成一个**本机常驻的只读客户端**，复用 `~/cloak-env` 的 cloakbrowser 运行环境，但使用**独立 profile**；对外提供 CLI / REST / MCP / SKILL 四种形态，供 Agent 与其他业务系统调用。
- 参照物：`tanji-client`（探迹 AI 拓客本地客户端）的架构与工程约定。
- 既有资产：`fuma-sales-dsh` 中已有 BOSS直聘 `boss_zhipin` 平台 CLI（岗位搜索 / 岗位详情 / 公司详情），2026-10-24 实测过；本项目的定位是**独立客户端**，不替换、不阻塞既有 CLI。
- 数据用途：按岗位关键词（如「外贸」「国际贸易」「海外销售」）找到**正在招这类岗位的公司**，结合公司详情/工商信息形成销售线索；只读，不写 CRM、不投递、不沟通。

## 1. Round 1（范围类）

| 问题 | 用户结论 |
| --- | --- |
| Q1 与既有 BOSS CLI 的关系 | 独立做 boss-client，与既有 CLI 独立，**完全不冲突**；对标 tanji-client |
| Q2 图中语义 | `name search` = **岗位搜索**；`company list` = 搜索结果去重后的公司列表；`status` 合并为一个 |
| Q3 能力边界 | 要 `company detail`，而且要**全**；**只读** |
| Q4 登录方式 | 支持**扫码 + 短信验证码两种**；**默认短信验证码**；二维码 **CLI 直接渲染**，REST 返回 **Base64** |
| Q5 账号/城市/筛选 | 默认**单账号**，架构预留多账号；**默认城市可配置、支持多城市**；暂时不需要其他筛选 |
| Q6 接口/部署 | 与 tanji-client 同构（CLI + REST + MCP + SKILL；端口 8790；127.0.0.1 + Bearer；systemd） |
| Q7 数据保留 | **只保留结构化缓存**；缓存保留规则由实现方设计 |

## 2. Round 2（登录与链路实测，2026-11-11）

> 详细记录、请求/响应、页面顺序见 [实测记录](../exploration/2026-11-11/REPORT.md)。
> 实测环境：非无头 cloakbrowser 0.6.5 + Chromium 146，独立 profile `~/.boss-client/profile`，真实账号（求职者身份）。

| 主题 | 实测结论 |
| --- | --- |
| 二维码登录 | 登录页 `.qr-code-box img` 是 `blob:` 地址，页面内可取出 PNG（200×200、3136 bytes）；REST Base64 / CLI 渲染均可行 |
| 短信登录 | 手机号 + 发送验证码 → **极验 v3** → 提交 6 位码；实测成功 |
| 验证码 | 遇到「点选（请在下图依次点击）」与「滑块（拖动滑块完成拼图）」两种；必须由真实浏览器通过，不能裸 HTTP 绕过 |
| 会话 | profile 持久化有效，关浏览器/重启进程可复用登录态；`wt2/zp_at` 约 10.6 天到期，`__zp_stoken__` 约 3 天 |
| 岗位搜索 | `POST /wapi/zpgeek/search/joblist.json`；`page/pageSize/city/query/scene`；实测 `resCount=450`、`totalCount=300`（展示上限）、`hasMore=true`、15 条/页；`page=2` 正常 |
| 岗位详情 | `GET /wapi/zpgeek/job/detail.json?securityId=...`；返回 `jobInfo/bossInfo/brandComInfo` |
| 公司详情 | `/gongsi/<encryptBrandId>.html` 为 SSR HTML；可提取完整工商信息 + 热招职位 + 招聘者 + 简介 |
| 公司全部职位 | `/gongsi/job/<encryptBrandId>.html`；实测 11 条 |
| 公司列表 | 岗位结果按 `encryptBrandId` 去重；石家庄第 1 页 17 个岗位链接 → 16 家公司 |
| 公司频道 `/gongsi/` | 存在，按城市/行业/融资阶段/规模筛选；不是岗位结果聚合，v1 不纳入 |
| status | 求职者侧**没有额度**；status 应为登录态 + 会话剩余时间 + 风控冷却 + 请求计数 + 缓存统计 |
| 风控 | 本轮中等强度未触发 `code 37`；继承既有结论：单并发、页间延迟、单任务 ≤5 页、code37 冷却 |

**最大的产品约束**：BOSS 登录有极验，**首次登录/掉线重登无法做到无人值守**。客户端能做的是把「二维码 / 验证码截图 / 点击坐标 / 短信码」通过 headful 浏览器或 REST 中继交给人工/外部 agent 完成；**不把“自动破解极验”作为 PRD 必达项**。

## 4. 决策与矛盾处理

1. **“自动登录” vs 极验**
   - 原 Round 1 曾出现“7×24 自动登录”的预期；实测证明首次登录需要人工。
   - 结论：v1 承诺「首次/掉线人工一次 + profile 复用 + 心跳检测 + 失效提醒」，不承诺「首次无人值守自动登录」。
2. **boss-client vs fuma-sales-dsh 的 boss_zhipin CLI**
   - 结论：两者独立；boss-client 不替换既有 CLI。后续如需统一，可由 fuma 侧改为调 boss-client 的 REST/CLI（不在本期范围）。
3. **company list 的语义**
   - 结论：只做「岗位搜索结果按 `encryptBrandId` 去重后的公司列表」，不做 `/gongsi/` 公司大全频道（v2 候选）。
4. **status 的语义**
   - 结论：合并 `check status` / `status` 为一个；求职者侧无额度字段，不照搬 tanji 的 quota。
5. **数据保留**
   - 结论：只做结构化缓存（SQLite），不落 raw 响应/HTML 证据链；登录过程的 QR/验证码截图仅临时保留（内存/临时文件，600 权限，TTL 后删除）。
6. **默认登录方式**
   - 结论：默认短信验证码；二维码作为可选模式；两种都支持 headful 人工与 REST 中继。
7. **城市与筛选**
   - 结论：单账号、多城市可配置（cityCode 注册表）；v1 不做薪资/经验/学历/行业/规模/融资阶段筛选。
8. **接口与部署**
   - 结论：与 tanji-client 同构；端口 8790；`127.0.0.1` + Bearer；MCP stdio；systemd user；单实例。
